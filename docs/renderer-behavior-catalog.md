# Renderer behaviour catalog — initial entries

This catalog describes observed runtime selection and behavior for the pinned extended spec. It is incomplete; [registry inventory](renderer-registry-inventory.json) lists all entries without certifying them. Material and Cupertino are separate renderer families. Tests cited below prove only their executed targets.

## Ordinary string and multiline Control

| Contract | Material | Cupertino |
| --- | --- | --- |
| Provenance | Kotlin renderer composition; ordinary JSON Forms `Control` and established `multi` option | Separate Kotlin Cupertino composition with the same portable option |
| Selection | String schema `Control`, tester rank 1; `multi: true` selects multiline rank 2. Password/date/time/date-time and other more specific testers can win. Generated UI schemas can select the ordinary string control. | Same conditions, with the Cupertino registry's rank offset of 100 (101/102). Its input and chrome are native Cupertino compositions. |
| Display and storage | String data is displayed in a Material text field. A committed empty edit removes the property unless a detail context preserves empty values. | Same storage rule; Cupertino uses its own `BasicTextField` composition. |
| Options | `multi` selects; `focus` requests focus once; `showUnfocusedDescription` controls help visibility; `hideRequiredAsterisk` controls only the visual marker; `clearable` controls the clear action; `restrict` guards edits above `maxLength`. Local options override config where implemented. | Same portable meanings. `focus`, description, and marker options require JSON booleans. |
| Schema and validity | `type: string` selects. `maxLength` is guarded on edits when restricted. Validator errors remain document errors; missing, null and imported non-string values are not evidence of a string. Required presence comes from the containing object schema. | Same portable constraints; validation remains separate from display. |
| Read-only, disabled and fallback | Text edits and Clear are blocked when read-only/disabled. A host-level read-only form currently disables inputs; `separateReadonlyFromDisabled` permits a locally read-only, focusable input. Unsupported schema types do not select this entry. | Same host limitation, with separate Cupertino control. |
| Accessibility and locale | Required state and visible help appear on the input's state description, and visible error appears on its error semantics. Built-in required/Clear strings use English or Bulgarian with host override. Direct screen-reader behavior remains unverified. | Same semantic and locale contract, with separate input composition. |

Selection example: schema `{"type":"object","properties":{"name":{"type":"string","maxLength":20}},"required":["name"]}` with UI schema `{"type":"Control","scope":"#/properties/name","options":{"multi":true,"showUnfocusedDescription":true}}` selects multiline string input. An incompatible schema `{"type":"object","properties":{"name":{"type":"number"}}}` with that UI schema does not select the string input; numeric selection applies. Source: [Material text](../material-renderers/src/commonMain/kotlin/com/chobantonov/jsonfroms/material/renderers/controls/MaterialTextControl.kt), [Cupertino text](../cupertino-renderers/src/commonMain/kotlin/com/chobantonov/jsonfroms/cupertino/renderers/controls/CupertinoTextControl.kt). Mounted [input tests](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/InputDescriptionUiTest.kt) and [focus tests](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/InitialFocusUiTest.kt) pass on JVM/iOS simulator.

## Schema/UI format conflicts

The combined registries evaluate every applicable tester. The highest rank wins; a tie keeps the earlier registry entry. Schema `format` remains a validation constraint even when a different UI presentation wins. These are the current string-control ranks:

| Presentation | Material rank | Cupertino rank | Selection source |
| --- | ---: | ---: | --- |
| Code fallback | 30 | 130 | UI `format: "code"`; preserves the native control beneath an unavailable-Monaco notice |
| Date, time | 4 | 104 | Matching schema or UI format |
| Color, duration, cron | 3 | 103 | Matching schema or UI format |
| Date-time, password | 2 | 102 | Matching schema or UI format |
| File | 2 | 102 | Schema `format: "binary"`/`"byte"` or `contentEncoding: "base64"` |
| Ordinary string | 1 | 101 | String-schema fallback |

The base registry lists Date before Time and Date-time before Password. Extended entries follow base entries in Color, Duration, Cron, File order. Thus schema `time` plus UI `date` selects Date (rank 4 tie); schema `date-time` plus UI `password` selects Date-time (rank 2 tie); schema `cron` plus UI `duration` selects Duration (rank 3 tie); and schema `byte` plus UI `password` selects Password (rank 2 tie, base entry first). A schema `date-time` plus UI `color` selects Color (rank 3 over 2). UI `code` selects the explicit unavailable-Monaco fallback (rank 30/130), while an unrecognized schema/UI format pair uses ordinary text. These outcomes are covered by the [combined-registry selection test](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/FormatConflictSelectionTest.kt). A paired [mounted conflict test](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/FormatConflictUiTest.kt) confirms schema `time` plus UI `date` shows the date picker, writes a date only after an edit, and keeps the schema's time-format validation error. The table describes renderer selection; it does not certify that every conflicting presentation is a useful authoring choice.

## Option source and precedence

Renderer selection reads UI-schema options and the resolved schema. Host config is available separately in tester context; config-only `format`, `multi` and `variant` values do not choose a specialized string presentation. A local UI password format wins over a conflicting config date value. During rendering, supported local scalar options override global defaults by key, including `false`, `0` and `""`. Layout, validation-indicator and dialog resolution use their documented per-option rules without mutating the authored Control options or nested host config. A [pure merge test](../core/src/commonTest/kotlin/com/chobantonov/jsonfroms/core/mappers/OptionMergeInvariantTest.kt) checks source identity and content; the [registry test](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/FormatConflictSelectionTest.kt) checks selection, and paired [mounted input tests](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/InputDescriptionUiTest.kt) keep local `showUnfocusedDescription: false` over global true.

Read-only, confirmation and validator selection use dedicated contracts. Form-wide read-only wins before applicable rules, UI options, config, schema `readOnly` and inherited props; the [cell mapper regression](../core/src/commonTest/kotlin/com/chobantonov/jsonfroms/core/mappers/CellTest.kt) keeps form/UI read-only effective even when an inherited cell prop is false. Confirmation resolves element mode, then renderer-specific mode, then namespaced form default, then operation fallback, as tested in [ConfirmationPolicyTest](../core/src/commonTest/kotlin/com/chobantonov/jsonfroms/core/confirmation/ConfirmationPolicyTest.kt). The validator engine is supplied through core initialization's explicit validator option or the shared Kotlin default; generic UI options do not replace it.

Material input chrome uses `options.material.inputVariant` (`standard`, `filled`, `outlined`) and the form default `config.jsonformsExtended.material.inputVariant`. The local style wins, then the form default, then `outlined`. Portable `options.variant` remains a presentation selector; `variant: "filled"` and top-level `config.variant` no longer select Material input chrome. The [Material resolver test](../material-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/material/renderers/util/ThemeTest.kt) checks this namespace and precedence, while the [string cell tester](../core/src/commonTest/kotlin/com/chobantonov/jsonfroms/core/testers/PlainStringCellTesterTest.kt) checks that the Material namespace leaves ordinary string selection available.

## Composed and referenced control scopes

The combined Material and Cupertino registries resolve a Control scope through untyped `allOf`, `anyOf`, `oneOf`, `then` and `else` branches and referenced properties before selecting string or integer inputs. Reversing registry order keeps those typed winners, so the generic mixed control cannot intercept them. A root scalar `allOf` with one string branch also selects the ordinary string input. [Registry cases](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/ComposedScopeSelectionTest.kt) check selection, and [mounted cases](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/ComposedScopeSelectionUiTest.kt) edit `allOf`/`anyOf` fields, each active `oneOf` branch, and separate `then`/`else` paths without changing their JSON types.

Schema lookup normally takes the first matching path. For a Control whose scope consists of `properties` steps, including nested property paths, dispatch chooses a `oneOf` or `anyOf` branch when the stored field's JSON type matches exactly one candidate editing schema. If multiple candidates share that type, required sibling `const` fields may select a branch when every type-matching candidate declares such a discriminator and exactly one matches the edited field's parent object. This also applies when that parent is nested under the current form or array row. The lookup starts at the Control's data context, including an expanded array row or a selected ListWithDetail row. A host replacement can switch editors without writing data; the next edit stores a value at the same path. Flat object-array items whose alternatives declare the same scalar fields form table columns; each row selects its cell schema from its own stored value and required `const` discriminators, whether the table is automatic or explicitly requested. Distinct flat scalar fields also form automatic table columns when all branches have unique required scalar `const` values for one discriminator; Add offers a branch choice. An imported row with a missing or unknown discriminator can choose a branch in its enum cell without losing its other fields. Nested or non-discriminated distinct alternatives retain expandable details. Missing values, unresolved ambiguity and unsupported predicates keep first-match lookup. An authored property schema, required marker for that property, or additional `allOf`/conditional contract in the dispatch schema retains its existing precedence. Whole-form validation always uses the original schema. [Array-shape registry tests](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/ArraySelectionTest.kt), [pure branch tests](../core/src/commonTest/kotlin/com/chobantonov/jsonfroms/core/util/ActiveEditingSchemaTest.kt) and [mounted host-replacement tests](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/ComposedScopeSelectionUiTest.kt) cover this bounded contract. Other predicates and ambiguous matches remain open.

A Control at a root `allOf` remains an `allOf` form and dispatches its branches. A Control scoped to an array property declared inside an `allOf`, `anyOf`, `oneOf`, `then` or `else` branch selects the array's default presentation: flat object rows use a table, nested object rows use expandable details, and an explicit table option overrides the nested default. [Registry selection](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/ArraySelectionTest.kt) checks both registry orders. [Mounted editing](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/DefaultArrayShapeUiTest.kt) covers both families and retains the original array-row path and whole-schema validity in each distinct active branch.

## Specialized selection over generic fallback

The [combined-registry matrix](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/SpecializedSelectionTest.kt) checks both registry orders in Material and Cupertino. Free-string plus enum `anyOf` selects suggested-string input; const-only titled `oneOf` selects finite choice; plain enum, password and bounded slider select their specialties. Finite-only `anyOf` and object `oneOf` retain composition renderers, while a password option on an integer and a slider option without all required bounds retain the integer input. These are applicability checks as well as priority checks; a variant option alone cannot make an incompatible schema match.

## Enum-array selection and explicit tables

For ordinary arrays, the combined registries select an editable table for primitive rows and flat object properties, and an expandable detail renderer for nested object properties. An authored `table: true` selects the table for a nested object array. The [shape selection test](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/ArraySelectionTest.kt) checks these four outcomes in both families. The [mounted shape cases](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/DefaultArrayShapeUiTest.kt) check one editable primitive cell with no redundant value heading, flat property columns, and the nested item's header plus detail field.

An array with `uniqueItems: true` and finite string item choices defaults to the checkbox-array renderer in both families. An authored `table: true`, array-valued `columnDefs`, or `variant: "ag-grid"` selects the array table instead; the latter uses the documented unavailable-grid fallback outside the web component. The table dispatches enum item editors through the cell registry. Authored `chips` and `multi-select` retain their own array presentations. Config-only table, column definitions or variant values do not select a renderer. The automatic checkbox tester has rank 4, below explicit table/column/grid rank 5 and chips/multi-select rank 6. [Combined-registry tests](../extended-renderers/src/commonTest/kotlin/com/chobantonov/jsonfroms/extended/renderers/ArraySelectionTest.kt) and [mounted table tests](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/EnumArrayTableSelectionUiTest.kt) cover these choices. The [default-shape mounted tests](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/DefaultArrayShapeUiTest.kt) also add and delete primitive, flat-object and nested-object rows without an authored presentation. Primitive strings start as `""`; object rows start as `{}` when properties declare no defaults. Each action makes one write and updates `minItems` validity. Invalid string values in all three default shapes show an accessible error indicator, and a row edit at the original path clears that error and restores validity.

Flat object alternatives select the automatic table when every `oneOf`/`anyOf` branch has a unique required scalar `const` discriminator, whether their other fields are shared or distinct. Numeric constants use exact decimal value equality, so `1`, `1.0` and `1e0` cannot masquerade as separate branches. The discriminator column offers the branch values, branch-only columns render only on applicable rows, and Add opens a branch menu so a new row starts with the chosen discriminator and its authored defaults. An open menu closes after host array replacement. Ambiguous or nested alternatives retain expandable details. The mounted [branch-table cases](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/ComposedScopeSelectionUiTest.kt) cover Material/Cupertino row editing and English/Bulgarian menu labels.

The combined-registry tests also resolve a Control scope through both an outer array reference and an item reference before selecting automatic checkboxes or an explicit table. Positional arrays select the tuple renderer, including an explicit tuple request. A scoped `ListWithDetail` selects its family renderer for a referenced object array; primitive and positional arrays do not match that presentation. An invalid explicit tuple request remains routed to the tuple configuration diagnostic under its own contract.

## Password Control

Schema or UI `format: "password"` selects a masked string input in both families. A localized reveal button changes only presentation; Clear remains a separate action and is unavailable in read-only mode. Password edits share the ordinary text `maxLength` restriction guard, including recovery from an overlong imported value and local `restrict: false`. Six [password tests](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/PasswordLocaleUiTest.kt) pass on JVM and iOS simulator. When `variant: "otp"` has both `minLength` and `maxLength`, the control uses `maxLength` boxes around one keyboard-editable string; a missing bound falls back to the ordinary password field. Twelve [OTP tests](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/OtpPasswordUiTest.kt) pass on JVM and iOS simulator for partial-code validation, leading zeros, arrow-key insertion, full replacement, reveal, clear, narrow action reachability, imported overflow recovery, ordinary masked table cells and fallback. The renderer code compiles for JS and Wasm. Actual clipboard paste, large box counts, browser/device interaction and direct masking/IME evidence remain open.

Ordinary password and OTP controls distinguish missing data from an imported non-string JSON value. Both families show the actual invalid null or number in a visible, accessible English/Bulgarian marker while valid strings keep the masked input behavior. Four [mounted imported-value cases](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/PasswordInvalidValueUiTest.kt) pass on JVM with live locale/host replacement and explicit correction; other targets remain to verify.

In object-array tables, unambiguous password schema/UI formats now dispatch to compact Material or Cupertino password cells. They keep the family input, masking, reveal, Clear and restricted editing, while the table supplies the single column label. An authored per-column OTP variant uses the same ordinary masked cell, as required by §18.24; standalone OTP still uses boxes. [Tester cases](../core/src/commonTest/kotlin/com/chobantonov/jsonfroms/core/testers/PlainPasswordCellTesterTest.kt) reject conflicting formats, unrelated types and composed/enum schemas. Four [mounted cases](../examples-compose/src/commonTest/kotlin/com/chobantonov/jsonfroms/examples/compose/PasswordCellUiTest.kt) pass on JVM, iOS simulator, JS browser and Wasm browser for schema/UI dispatch, invalid imports, live Bulgarian text, reveal without a data write and max-length restriction.

## Generic combinator branch selection

An explicitly typed scalar with only validation or annotation keywords in its oneOf, anyOf or allOf branches uses the ordinary scalar renderer once. An allOf can also establish one scalar type through a definition reference when every branch has only scalar constraints or annotations and no type conflicts. The input keeps the outer control path and presentation while validation still uses the original composed schema. Distinct typed forms, const choices and editor-shaping keywords keep their specialized or generic branch presentation. The imported attendee anyOf and seats-per-table oneOf each render one numeric input in paired Material/Cupertino JVM and iOS simulator tests; invalid edits show field errors that clear on correction. The Draft-07 metaschema's referenced minLength allOf renders one labelled integer editor in paired JVM and iOS simulator tests. Default numeric restriction intersects compatible allOf bounds, leaving a rejected negative draft local; an explicit unrestricted edit commits it and exposes the full metaschema error. OneOf/anyOf branch bounds are never merged into native prevention.

Generic `oneOf` and `anyOf` controls match stored data against branch structure before choosing a detail editor. Branch validation includes the root schema's `definitions` and `$defs`, so a branch whose child uses a local reference can be selected without falling back to the first branch. An exact structural match takes priority; when none exists, matching immediate fields retain the surrounding branch while a descendant is invalid. Arrays whose items resolve to a combinator and closed arrays with `items: false` select the portable array editor. The imported five-level tree renders all five Folder branches and arrays in paired Material/Cupertino JVM and iOS simulator tests; Add is enabled above the limit and disabled at level five, with no mount write. An imported sixth-level file retains a Delete action; confirming it restores the valid tree. Other root-local reference paths and mounted browser interaction remain unverified.

`allOf` now dispatches the enclosing object's properties before each branch form in schema order. Cupertino uses its own combinator renderer and error text while sharing the nonvisual property dispatch helper. The imported equipment control shows Projector, its asset tag and working state without a mount write in Material and Cupertino JVM/iOS tests. Registered combined detail schemas and branch editing remain to verify.

Generic `anyOf` uses native Cupertino buttons for its branch strip, with selected semantics and horizontal scrolling. The stored value still picks a fitting branch; changing tabs does not rewrite data. Mounted tests cover branch editing, readonly navigation, missing data and host replacement.

## Duration control

The shared extended duration renderer selects string Controls with schema `format: "duration"` or UI `options.format: "duration"` for both Material and Cupertino. Its picker accepts non-negative exact integer years, months, days, hours, minutes and seconds, or a separate weeks-only value. It no longer caps these quantities to clock ranges. `showActions` defaults true: a translated trigger opens Material or Cupertino's native alert dialog, Cancel restores the existing value, and OK writes only after an edit with valid fields. Untouched OK closes without a data write. `showActions: false` keeps the component editor inline and commits valid edits immediately.
